# Algorithm decision

**Decision recorded 2026-10-06:** keep the MoonBit-native event and causal
model with indexed incremental materialization. Keep the optional
fixture-tested, sequential Yjs semantic projection separate from the native
core; no Yjs API or wire-format compatibility is claimed. Do not copy Yjs's
JavaScript struct store into the native core. Retain the event-log replay
prototype as a correctness oracle and as a candidate for cold projection work.

This is a bounded Phase 2 decision, not a claim that the indexed implementation
is the fastest option for every workload. The replay projector is faster at
reconstructing visible snapshots from the tested small, complete event logs,
while the Yjs struct-store candidate adds a same-edit reference under its own
public update path. Neither comparison implements the full Document contract.
Replay omits causal validation, pending events, relative positions, incremental
local editing, state-vector diffs, checkpoint restore, and compaction. Yjs
decodes and integrates encoded updates with its own semantics. These results
inform cold materialization and candidate choice without establishing a
universal throughput winner.

## Candidates measured

The production candidate applies a valid event set with Document::apply_events
into the existing indexed representation. It validates and retains history,
updates sequence indexes and map registers, and builds the replica frontier.
The timed receiver starts empty for each sample. The API also clones state for
atomic staging, validates dependencies and duplicates, drains pending events,
commits the state, and computes a change set. The benchmark has no observers
registered, so there are no observer callbacks in the measured path.

The independent replay candidate in bench/measure/replay_wbtest.mbt sorts a
complete checkpoint-free log by Lamport time and event ID, records map
versions and sequence nodes in ordinary maps, then resolves visible map values
and walks sorted sequence children into text/list projections. It does not
call production integration or sequence-index code. It assumes a complete
valid log and does not implement equivalent dependency/duplicate validation,
pending-event handling, atomic mutable-document staging, change-set creation,
or observer dispatch. It rejects checkpointed logs and is intended only for
the valid synthetic histories generated by the benchmark.

The correctness check compares the map, list, and text projection for every
root touched by the input event log. It covers a seed replica plus two offline
branches that independently edit text and lists and race on map keys. The
white-box test also checks event, replica, sequence-node, tombstone, and
map-version counts. It is a deterministic scenario test, not a proof over all
delivery schedules; permutation and duplicate-application tests remain in the
main CRDT suite.

The Yjs 13.6.32 struct-store candidate consumes the same deterministic
high-level operation trace from `bench/workload`. It uses stable client IDs for
the seed and two branches, encodes branch deltas relative to the seed state
vector, then checks Yjs convergence and visible projections with the two deltas
applied in both orders. The output reports Yjs and native projections side by
side and marks whether they match; it does not assert that native and Yjs must
select the same map winner or sequence order. Its cold timing includes creating
a fresh Y.Doc, decoding and integrating the seed and branch updates with
`Y.applyUpdate`, and reading the visible projection. Scenario edits and update
encoding happen before the timer. Native receives decoded Event values and
includes causal validation, atomic staging, pending-event drain, and change-set
creation, so the timings do different work and are not equivalent end-to-end
throughput measurements.

standard deviation).

Within these three sizes, the indexed receiver takes about 6.4–6.7 times the
replay projection time on native, 8.9–9.3 times on JavaScript, and 6.3–6.7
times on Wasm GC. Both implementations grow with event count. Because they
perform different work and only the first produces a mutable indexed Document,
these ratios are workload timings, not general CRDT throughput ratios.

The JavaScript-only Yjs candidate ran on Node 26.8.2 with the same shared
logical operation trace and stable seed/branch client IDs. Its measured path
constructs a fresh `Y.Doc`, decodes and integrates a prepared seed update and
two branch deltas, and reads the visible projection. Scenario construction and
update encoding are outside the timer. The table reports the median across 15
samples after five warmups and the observed range.

| Native events | Logical edit calls | Yjs stored structs | Yjs update bytes | Yjs cold merge + projection (µs) |
| ---: | ---: | ---: | ---: | ---: |
| 85 | 58 | 38 | 359 | 125.250 (101.458–401.333) |

Yjs converged under both branch-update orders in every workload, and the final
Yjs projection matched the native projection in all three tested cases. The
struct count and native event count use different units because Yjs can group
text content into fewer structs. These timings also do different work: Yjs
decodes encoded updates, while the native indexed API receives decoded Event
values and includes validation, atomic staging, pending-event drain, and change
set construction. The measurements do not establish equivalent sync
throughput or Yjs semantic compatibility.

The independent replay prototype remains a useful correctness oracle and a
cold-projection candidate. The Yjs comparison adds a pinned upstream
struct-store implementation, but its encoded-update integration path differs
from the native pre-decoded event path. The architecture choice is a bounded
MoonBit-native core decision based on implementation contract, reproducible
behavior, and these scoped measurements, not a claim of a three-way speed win.

The fixed-live history workload keeps 32 text scalars, four list values, and
two map keys constant while retained history grows from 38 to 2,086 events per
document. Its three-backend setup-inclusive construction and compaction timings,
logical storage counts, and encoded checkpoint sizes are recorded in
[benchmarks.md](benchmarks.md). A separate JavaScript heap probe observed
median retained `heapUsed` deltas of about 77 KB to 3.30 MB per document before
compaction, and about 17–37 KB afterward. Those are process-level heap
measurements divided across eight live documents, not allocator bytes or exact
memory-per-element values; they are evidence from one workload and Node runtime.
The variable-live probe retains eight empty documents as a baseline, adds eight
populated documents, and divides the heap delta by visible text/list elements.
Because this delta includes each added Document's fixed object overhead, its
per-element value is an approximate whole-cohort estimate, not sequence-node
size. Across 128–4,096 combined visible elements per document, the measured
median delta declined from about 2,044 to 1,951 bytes per element before
compaction and from about 528 to 429 bytes afterward.

The setup-excluded local-edit runner prepared a fresh 64-scalar seed before
each timer, then measured one public insert or delete call. Median times were
609/608 µs on native, 584/559 µs on JavaScript, and 347/269 µs on Wasm GC for
insert/delete. The 50-sample ranges are in [benchmarks.md](benchmarks.md); they
show host/runtime dispersion and are not product latency targets.

The selected architecture keeps the index for operations whose contract
depends on it, including incremental edits and relative positions. The replay
gap makes cold materialization a clear optimization target. Setup-excluded
single-edit latency and live-size process-heap evidence are recorded in
[benchmarks.md](benchmarks.md). Before replacing indexes or introducing a
replay-backed runtime path, compare larger documents, more independent
branches, and checkpoint-based restore while requiring equivalent validation
and API behavior.

## Revisit conditions

Reopen this decision if a replay-backed candidate implements the same causal,
position, update, and checkpoint behavior and still wins on representative
large-document workloads, or if indexed local edits / remote integration fail
the project's product latency targets. No product latency target has been set
yet.
